You are the senior backend architect and implementation engineer for our Smart India Hackathon project.

PROJECT:
SIH Problem Statement 26002 — Smart Logistics.

OBJECTIVE:
Build a production-quality MVP backend for an intelligent logistics platform that supports:
- User authentication
- Drivers
- Vehicles
- Shipments
- Route calculation
- AI-based route prediction
- Vehicle GPS tracking
- Incidents
- Weather information
- Alerts
- Historical trip data
- Realtime updates

IMPORTANT ARCHITECTURE DECISIONS:

1. Backend:
Node.js + Express + TypeScript.

2. Database:
MongoDB + Mongoose.

3. DO NOT USE:
- PostgreSQL
- PostGIS
- Prisma
- Kafka
- RabbitMQ
- Kubernetes
- Microservices architecture
- Custom road-routing engine

We want a modular monolith.

4. ROUTING:
Use OpenRouteService / openrouteservice API based on OpenStreetMap data for road route calculation.

The AI must NOT generate road geometry or invent roads.

OpenRouteService is responsible for calculating physically valid road routes.

5. AI:
AI will be a separate Python/FastAPI service.

The Node.js backend will call the AI service through HTTP.

AI responsibilities:
- Predict travel duration
- Predict delay
- Calculate delay probability
- Calculate route risk score
- Optionally explain major risk factors

6. WEATHER:
Weather data will be obtained by the backend from an external weather API and passed to the AI through structured features.

7. REALTIME:
Use Socket.IO for vehicle GPS updates and alerts.

8. GEOLOCATION:
Use MongoDB GeoJSON and 2dsphere indexes.

Coordinates must always follow:
[longitude, latitude]

9. FRONTENDS:
The backend must support:
- Next.js/React web frontend
- React Native/Expo mobile application

Both must communicate with the same backend.

ROUTE CALCULATION
==================================================

Implement:

POST /api/v1/routes/compute

Input:

{
  "origin": {
    "latitude": 26.1445,
    "longitude": 91.7362
  },
  "destination": {
    "latitude": 25.5788,
    "longitude": 91.8933
  },
  "vehicleId": "..."
}

The backend must:

1. Validate input.
2. Load vehicle from MongoDB.
3. Call OpenRouteService.
4. Request appropriate routing profile.
5. Receive route information.
6. Normalize the response into our own internal route format.
7. Store relevant route information in MongoDB.
8. Return route candidates to frontend.

Do not expose OpenRouteService response format directly to the frontend.

Create an abstraction layer:

RouteProvider interface

OpenRouteServiceProvider implements RouteProvider.

This makes it possible to replace the routing provider later.

SMART ROUTE PREDICTION
==================================================

Implement:

POST /api/v1/routes/predict

Process:

1. Validate request.
2. Load shipment.
3. Load vehicle.
4. Generate candidate routes using OpenRouteService.
5. Gather historical information from MongoDB.
6. Gather nearby incidents using MongoDB 2dsphere queries.
7. Gather weather information.
8. Build structured AI features.
9. Send candidates to Python AI service.
10. Validate AI response.
11. Rank candidate routes.
12. Save prediction.
13. Save recommended route.
14. Return complete result.

==================================================
AI RESPONSE CONTRACT
==================================================

Expect:

{
  "predictions": [
    {
      "routeId": "route_a",
      "predictedDurationMinutes": 238,
      "predictedDelayMinutes": 58,
      "delayProbability": 0.81,
      "riskScore": 0.84,
      "riskLevel": "HIGH"
    }
  ]
}

Validate:
- routeId
- numeric values
- probabilities between 0 and 1
- riskScore between 0 and 1
- valid riskLevel

If AI service is unavailable:
Return a graceful fallback based on routing-provider duration and available deterministic risk rules.

Never crash the entire backend because AI is unavailable.

==================================================
ROUTE RANKING
==================================================

Implement a deterministic ranking layer after AI.

Initial formula:

40% predicted travel time
30% delay probability
20% risk score
10% distance

Normalize values before scoring.

Make ranking configurable so weights can later be changed.

The AI predicts.
The backend makes the final business decision.

==================================================
FINAL END-TO-END BEHAVIOR
==================================================

The completed system must support this scenario:

A dispatcher creates a shipment from Guwahati to Shillong.

A truck and driver are assigned.

The backend requests candidate routes from OpenRouteService.

The backend gathers:
- route distance
- baseline duration
- weather
- incidents
- vehicle information
- historical trip information

The backend sends structured route features to the Python AI service.

The AI returns:
- predicted duration
- predicted delay
- delay probability
- risk score
- risk level

The backend ranks the routes.

The backend recommends the safest/best route according to configured business weights.

The frontend displays:
- route
- distance
- baseline ETA
- predicted ETA
- expected delay
- risk level
- incidents
- weather
- recommendation reason

During the trip, the driver sends GPS updates.

The backend:
- updates current vehicle location
- stores location history
- broadcasts location through Socket.IO

If a serious incident occurs near the route:
- create an alert
- notify dispatcher/driver
- optionally recalculate route
- run prediction again
- provide a new recommendation

The final architecture must be clean, maintainable, testable and suitable for an SIH demonstration.

Before implementing, inspect the existing project files and preserve useful existing code. Do not unnecessarily rewrite working components.

Start with PHASE 1 only.
